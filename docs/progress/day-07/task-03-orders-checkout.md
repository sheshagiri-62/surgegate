## 3. How it works

**Idempotency, simply.** Think of a restaurant order slip with a number. If the waiter brings
the same slip number twice, the kitchen cooks once and says "already got it". The browser makes
one random number (the *Idempotency-Key*) per hold and sends it with every try, so retries and
double clicks can't create a second order. The database enforces it with
`UNIQUE(buyer_id, idempotency_key)`. Even 20 requests arriving at the same moment end up as one
order: the test proves it.

**In SurgeGate:**

```
buyer app ──POST /book/{event}/orders  (pass + Idempotency-Key)──► CloudFront ─► ALB ─► booking API
                                                                                    │ lock the hold row
                                                                                    │ checks: mine, this event, active, ≥ 60 s left
                                                                                    │ amount = SUM(held seats) from PostgreSQL
                                                                                    │ INSERT order + order_items (commit)
                                                                                    └─► mock-pay POST /v1/orders (in cluster, Basic auth)
          ◄── {order_id, checkout: {type: redirect, url: …/mockpay/checkout/order_…}} ──┘
browser ──► CloudFront ─► ALB rule 5 (/mockpay/checkout/* + header) ─► mock-pay page ─► Pay
mock-pay ──► signed webhook POST https://<cloudfront>/webhooks/razorpay   (Task 4 handles it)
         └─► 303 back to http://localhost:3000/order/?id=… ─► page polls GET /orders/{id}
```

- **Why lock the hold row?** The hold timer's release (Task 2) updates the same row, so between
  "is it active?" and "create the order", the hold can't be released underneath us.
- **Why 60 seconds?** With less time left, the buyer would be sent to pay for seats about to be
  released. Paying would then always become a late payment, so it is better to say "hold again".
- **Why is the order created before the provider order?** If the provider is down, we keep a
  `pending` order with no provider ID and return 502. A retry with the same key finishes the
  same order, so no "orphan" provider order is created without a record on our side.
- **Why `GET /orders/{id}` outside `/book/*`?** The booking pass lasts 15 minutes and may expire
  while the buyer waits on the status page. Ownership is checked instead.
- **The page trusts only the API.** The redirect back carries `razorpay_payment_id` etc., but
  anyone can type a URL. The order becomes *paid* only when the signed webhook is processed
  (Task 4).

**Task 4 design, already in the schema.** The order worker, in one transaction:
1. It inserts into `payments … ON CONFLICT (provider_payment_id) DO NOTHING`. Nothing inserted
   means a duplicate webhook, so it stops.
2. It checks that every `order_items` seat is still `held` by `order.hold_id` and that the hold
   is `active`. If so, it sets the seats to `sold`, `order_items.sold = true`, the hold to
   `converted` and the order to `paid`.
3. If the hold was already released, it applies the late-payment rule (Task 5): re-hold the
   snapshot seats if they are free, otherwise refund.

**Note for Day 9 (WAF), required:** the WAF rules (rate limits, managed bot rules, challenge)
must **exclude `/webhooks/*`**. Webhooks are server-to-server calls from the payment provider.
They can't solve a challenge, come in bursts during a sale, and would look like bots.
Authentication there is the **HMAC signature**, not WAF. Blocking them would leave paid orders
unconfirmed. I also added this to the Day 9 line in the checklist.

## 7. Interview notes

- **Q:** How do you stop a double click from creating two orders?
  **A:** The browser sends an Idempotency-Key, one UUID per hold, kept in sessionStorage. The
  database has `UNIQUE(buyer_id, idempotency_key)`. The second request finds the existing order
  (or loses the insert race, catches the unique violation and reads the winner) and returns it
  with 200. A test fires 20 parallel creates with one key and gets one order and one set of
  items.
- **Q:** Why does the server compute the amount?
  **A:** Anything from the browser can be edited. The amount is the sum of the held seats'
  prices in PostgreSQL, and the mock charges the stored order amount. Sending `amount=1` in the
  checkout form changed nothing (verified live).
- **Q:** Why a mock instead of Razorpay, and is that honest?
  **A:** Razorpay test keys need business KYC (ADR 004). Everything that matters is real: the
  provider boundary, signed webhooks over the public edge, idempotency and the late-payment
  rule. Swapping to Razorpay is one class plus configuration. The mock even makes duplicate and
  delayed webhooks easy to trigger for the demo.
