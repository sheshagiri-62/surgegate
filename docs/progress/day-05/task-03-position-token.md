## 1. What the task was

Plan text: *"`position` endpoint returning a signed queue token (key in Secrets Manager)."*
Blueprint: the buyer receives a signed queue token holding their position, so refreshing the page
keeps the same place. Tokens are bound to the user and can't be forged or shared.

## 2. What I did, step by step

1. **`GET /queue/{event}/position`** (`sg_queue/position.py`), behind the JWT authorizer. The place
   is looked up by the **signed-in account**, so a refresh or re-join keeps it. Answers:
   - `202 joining`: joined, not sequenced yet;
   - `404`: not in the queue;
   - `pre-queue`: has a place, numbered at the start, no token yet;
   - `queued` or `admitted`, with:
     - `position`, `serving_up_to`, `ahead`;
     - `estimated_wait_seconds` (people ahead ÷ admission rate, rounded up to whole minutes;
       none while paused);
     - `queue_token`.
2. **`sg_queue/tokens.py`:**
   - **compact HMAC-SHA256 token**: `base64url(payload).base64url(signature)`;
   - payload `{typ, ev, sub, pos, iat, exp, kid}`, valid for 6 h;
   - `verify` checks, in order: format → key ID → **signature (constant-time compare)** → type →
     expiry → **the same user and event**.
3. **Key in Secrets Manager:** `surgegate/dev/queue/token-key` holds `{"kid": "v1", "key": …}`.
   - It's generated by an **ephemeral** `random_password` and written through the **write-only**
     `secret_string_wo`, so it is **never stored in Terraform state**.
   - The CI plan role doesn't need to read it (unlike redis-auth).
   - Rotation: bump `token_key_version`; tokens carry the `kid`.
4. **Lambda:** reads the key with its role (only that secret, plus `GetItem` on the table) and
   caches it for 5 minutes.
5. **Routes refactor:** the routes are now a map (`join`, `position`). A `moved` block kept the
   live join route rather than recreating it.
6. **Tests:** 15 new (32 total), with moto Secrets Manager.

## 3. How it works

**A signed note instead of a database lookup.** The token says "user X is number 57 in event Y,
until 01:00", and carries an HMAC signature computed with a secret key only our Lambdas know. Anyone
can read it, but changing even one character (say 57 → 1) makes the signature wrong. Copying it
doesn't help either: it names the user, and the admit step (Day 6) checks it against the caller's
own signed-in identity.

**Keeping the key out of Terraform state.** Normally a Terraform-generated secret is saved in the
state file. Here the value is *ephemeral* (it exists only during the apply) and goes into a
*write-only* field that Terraform sends to AWS but never stores. Terraform only remembers the
version number. Fewer copies of the key, and fewer people and roles that can read it.

## 7. Interview notes

- **Q:** Why sign the queue position instead of just storing it?
  **A:** It's stored too, but the signed token lets later steps (admit, and the CloudFront check
  for the booking pass) trust the position without another database read, and it makes refreshes
  cheap. HMAC makes it tamper-proof; binding it to the user and event makes it useless to anyone
  else.
- **Q:** How do you keep the signing key secret, even from your own tooling?
  **A:** It's in Secrets Manager, readable only by the functions that sign or verify. Terraform
  creates it through a write-only attribute fed by an ephemeral value, so it isn't even in the
  state file. Tokens carry a key ID, so the key can be rotated.
- **Q:** Why compare signatures with `compare_digest`?
  **A:** A normal `==` can stop at the first different byte, so response timing could leak how much
  of a forged signature is right. `hmac.compare_digest` always takes the same time.
