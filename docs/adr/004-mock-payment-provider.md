# ADR 004 — A Razorpay-shaped mock payment provider instead of Razorpay test mode (for now)

- **Date:** 2026-11-24
- **Status:** Accepted
- **Related:** blueprint "Payments and idempotency", "Hold timer"; implementation plan Day 7
  Tasks 2–4 and M4; [ADR 003](003-cloudfront-default-domain-in-front-of-alb.md) (edge routing)

## Context

The blueprint and plan use **Razorpay test mode** for checkout and webhooks. Razorpay won't
issue test-mode API keys to this account without business KYC, and there is no business to
verify. M4 still needs to show four things:

- a buyer pays;
- a webhook confirms the order exactly once;
- a duplicate webhook changes nothing;
- a late payment follows the late-payment rule.

Constraints:

- Nothing new that bills by the hour; the project budget is under $50.
- No secrets in Git; secrets live in Secrets Manager (CLAUDE.md rule 2).
- Switching to real Razorpay later must not change the booking API's order logic, the
  database schema or the webhook handling.

## Decision

1. **A `PaymentProvider` interface in the booking API**:
   - `create_order(amount_paise, currency, receipt)` returns the provider order ID and how the
     buyer pays (a checkout descriptor);
   - `verify_webhook_signature(raw_body, signature)` returns `bool`;
   - Task 4 adds `refund(payment_id)` for the late-payment rule.

   There are two implementations:
   - `MockProvider` now;
   - `RazorpayProvider` later, using the same interface and keys from
     `surgegate/dev/data/razorpay`.

   An environment variable `PAYMENT_PROVIDER=mock|razorpay` picks one.
2. **The mock is a small FastAPI service in the cluster** (`services/mock-pay`), with its own
   Helm chart and Argo CD application: one small pod on the existing nodes. It copies
   Razorpay's shapes, so the booking API code stays the same either way:
   - `POST /v1/orders` with HTTP Basic `key_id:key_secret` returns an `order_…` object
     (`id`, `amount`, `currency`, `receipt`, `status`).
   - The browser opens a **test checkout page** with *Pay success* and *Pay fail* buttons.
   - The mock sends a webhook with Razorpay's payload shape (`payment.captured` /
     `payment.failed`) and headers:
     - `X-Razorpay-Signature` = hex HMAC-SHA256 of the **raw body** with the webhook secret;
     - `X-Razorpay-Event-Id`.
   - **Test switches** on the page and on a test API: delay N seconds, send the webhook
     twice, wrong signature.
3. **One secret, generated by Terraform.**
   - `random_password` values go into the existing `surgegate/dev/data/razorpay` secret as
     JSON: `key_id`, `key_secret`, `webhook_secret`.
   - The mock and the booking API both read the secret with their own pod roles.
   - The value is never printed or written to Git.
   - Terraform ignores later changes to the value, so real Razorpay test keys can replace the
     mock ones by hand without Terraform overwriting them.
4. **The mock is a dev/test tool only.** Anyone who can open its page can "pay" in dev, exactly
   as anyone can in Razorpay test mode. The booking API never trusts the browser: an order
   becomes paid only from a webhook whose signature checks out (Task 4).
5. **Repo layout addition:** `services/mock-pay/` and `deploy/helm/mock-pay/`. They are not in
   the plan's layout; this ADR is the record of why.

## Consequences

- **Good:**
  - Every M4 check can be demoed, including duplicate and late webhooks.
  - The mock makes these cases easier to trigger than real Razorpay, where duplicates and
    delays can't be forced.
  - No new hourly AWS cost.
- **Good:** the interview story stays honest. The idempotency, signature and late-payment logic
  are real; only the provider is simulated. Swapping it is a configuration change plus one
  class.
- **Cost:** a small pod (requests 25m CPU / 64 MiB) on the existing nodes. The image costs a few
  MB of ECR storage, about $0.01/month. Webhooks go out through the existing NAT gateway, a
  negligible amount of data.
- **Limits:**
  - The mock keeps its orders in memory (one replica); a pod restart forgets unpaid mock
    orders. The booking API's own orders are unaffected.
  - The mock doesn't simulate UPI/card screens, Razorpay's dashboard or settlements.
- **Later:** with real Razorpay keys, set the secret by hand and `PAYMENT_PROVIDER=razorpay`.
  The buyer app opens Razorpay's checkout.js instead of the mock page; the checkout descriptor
  already tells it which one.

## Alternatives considered

| Option | Why not |
| --- | --- |
| Razorpay test mode (the plan) | Blocked: test keys need business KYC |
| Stripe test mode | Sign-up is also tied to a business for India; a different API shape from the blueprint's Razorpay flow |
| Fake payments inside the booking API (no separate service) | Hides the real boundary: no outbound API call, no inbound signed webhook over the edge |
| Mock as a Lambda + function URL | Possible, but adds an AWS resource and a public URL; a pod on the existing nodes costs nothing extra and deploys like the booking API |
